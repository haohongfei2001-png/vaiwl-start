# Free V1 · 本地工作空间合同修订

合同：`VAIWL-START-FREE/1.0`；修订：`2026-11-02-local-first`。授权依据：2026-11-02 用户明确要求“产品合同纠偏与真实可用版本收口”。本修订是对旧 M0 约束的正式范围变更，无需重复审批；原首页视觉、30 日历日算法、数据库 v1 与账号安全边界继续有效。

## 1. 目标与完成声明

已有历史立即形成可浏览、可搜索、关闭标签后仍可重开的本地工作空间；可靠的局部 Project 信息随正常浏览逐步生效。账号、当前 workspace、正式 PROJECT、正向 NONE 不再构成所有 Free 能力的共同开关。

`LOCAL_WORKSPACE_READY` 表示代码提供这些独立本地能力，实际可用性仍以同 SHA 测试和实机记录为准。正式原生归属以及完整 Chrome/Edge 旅程继续分别验收，不能把本地候选、合成夹具或绿色 CI 声明为真实来源通过，也不据此声明 `FREE_V1_ACCEPTED`。

## 2. 每项放宽的语义、安全条件与风险

| 变更 | 新数据语义 | 继续保留的条件 | 新误判风险与明确限制 |
|---|---|---|---|
| 账号未确认也展示 | 本地浏览器 Profile 的未分配目录，名称“本地历史” | 不创建假账号，不将未知历史自动归入当前已确认账号；按 Profile、scope 分离 | 同一 Profile 的历史可能来自多个账号；本地目录不声称账号归属 |
| UNKNOWN 按浏览日期组织 | `browserLastVisitAt` 仅决定“历史浏览／归属待确认”窗口 | 不改 membership，不写 OpenDay，不填活动索引；日期无效/缺失/未来则保留无日期入口 | 浏览日期可能含刷新、恢复、同步或重复访问，不能解释成主动使用 |
| UNKNOWN 可有真实打开活动 | 本地独立 OpenDay；时间窗为“主动打开／归属待确认” | 活动只落原记录，后续账号绑定不得迁移旧活动；同日每会话去重 | 有活动仍不证明原生 PROJECT/NONE 或账号 |
| Start 用浏览器导航确认 | 用户主动打开精确会话入口；不声称阅读、发送或正文完成 | 真实手势、唯一 intent、精确目标、首个文档绑定、导航完成、会话/session/epoch匹配、失败拒绝、提交前权限检查与事务内采集检查 | 同 URL 的应用错误页或权限提示可能已完成浏览器导航；活动只表示主动打开，不自动把 availability 改成 reachable |
| 局部 Project 观察可用 | `localProjectCandidate` 是有边界的本地候选，membership 仍 UNKNOWN | 精确 Project ID/URL、原生名称叶与限定成员关系；不同观察边界不合并；不按名称或 AI 猜测 | 页面结构变化、未确认账号使其不具备认证原生归属；始终显式标候选 |
| 各来源独立验收 | 可用本地能力继续运行，未证正式归属只关闭自身能力 | 真实来源不能由 fixture、runtime 开关或候选自动升级 | 候选收录不等于完整账号项目清单；未观察到的项目不会凭空出现 |

## 3. 归属与时间分离

正式 `PROJECT` 进入对应已确认 scope 的 Project 卡；正式 `NONE` 按最后确认主动打开日期形成“无项目”日期窗。只有浏览记录、尚无主动打开的正式 NONE 仍在“尚无主动打开记录”入口，不能冒充正式活动日期。

`UNKNOWN` 有有效本地活动时，优先按该活动日期进入“主动打开／归属待确认”；否则使用有效 `browserLastVisitAt` 进入“历史浏览／归属待确认”。没有有效日期时保留可搜索、可打开的独立无日期入口。两种日期来源均采用原固定 IANA 时区、每段 30 个当地日历日公式，空段不跳过；日期来源在界面上分别标明。

本次只修改投影与必要写入链，不把旧浏览时间回填到 `activity`、`openDays` 或 `lastActiveAt`。同一记录获得新的可靠归属后，投影只出现于适用的一个位置；不因日期分组或候选分组创建新会话。既有记录 key、去重及墓碑保留。账号绑定仍遵守既有 scoped-key 与逐条 CandidateResolution 的安全规则，不能把一条账号证明扩展到整批历史，不能搬移旧本地活动。

正式项目按已确认活动排序；待确认历史窗内部按浏览时刻、stableRank、key 排序。候选项目可用成员的有效主动打开时间，否则用浏览日期决定显示段；该值为显示时间 `latestDisplayAt`，不是已确认的项目活跃时间。候选项目仅在最新成员对应段出现，旧成员保留在父卡中。

## 4. Start 主动打开的当前生产链

1. Start 的真实 click、Enter 或辅助点击生成并持久化唯一 OpenIntent，再派发精确会话 URL。记录签发时的时区与本地日期，保留原生修饰键行为。
2. 第一次有效 `webNavigation.onCommitted` 冻结目标 top-frame 文档和 route。后来的刷新、恢复、错误目标或迟到文档不得替换该绑定。
3. `webNavigation.onCompleted` 与当前精确 frame/document/URL 匹配后，按 `confirmationBasis: 'browser-navigation'` 提交。`onErrorOccurred`、错误会话、登录页重定向、过期或账号冲突拒绝。
4. 原子消费 intent，并按 `[recordKey,timeZone,localDate]` upsert OpenDay。同日再次明确打开可更新最后时刻，活动单位仍为 1。无新意图的刷新、恢复、tab 激活和后台加载均不记。用户明确后台打开仍是主动意图。
5. 提交事务再次检查 `captureEnabled`；撤权、停止收录、session/epoch 变更不能让旧事件写入。worker 正常休眠可恢复尚有效的绑定，浏览器重启或扩展 Reload 使旧 pending intent 失效，已提交活动和历史仍持久化。

**当前可独立完成的生产路径是未分配记录的 Start 导航活动。** 对预期已确认 scope 的记录，当前账号/owner 证据仍是提交条件；没有可用的当前见证则不向该账号库记活动，也不借本地库绕过该边界。原生 ChatGPT 链接与地址栏入口仍是独立未启用能力，不阻塞 Start 入口。

`onCompleted` 不承诺 ChatGPT 正文可读、应用请求成功或用户阅读完毕。代码不得因此将未知可用性自动提升为 `reachable`；需要这些声明时必须另有匹配语义的来源。HTTP 缓存不自证意图；BFCache 若没有匹配的完成证据可保守漏记，不为追求计数而接受自动恢复。

## 5. 局部 Project 候选与正式 Project

沿用已授权 ChatGPT 页面里的严格、无正文元数据边界。只接受明确 Project ID、原生名称和可限定的成员链接；侧栏旁边历史链接、普通 `/c/` URL、标题相似及缺字段不证明成员或 NONE。不要求一次取得完整账号项目目录。

会话的可选字段 `localProjectCandidate` 为 `{key,projectId,nativeTitle,canonicalUrl,observedAt,basis:'local-project-observation'}`。其 key 由本地 Profile、browser session、binding、observationId 和 Project ID 共同隔离，**不跨观察合并**。候选挂在原有未分配 UNKNOWN 会话上，不写入正式 `projects` store、不授予 verified/scope 权威、不修改会话 key。

候选卡显式显示“本地候选项目／原生归属待确认”，可以展开旧成员、搜索候选原名、打开原生 Project URL。其成员只显示一次，不同时留在独立日期卡中。正式 PROJECT/NONE 不受候选覆盖；冲突/撤销证据不继续作为候选分组依据。观察粒度较保守时，同一原生 Project 的不同观察可能形成多个本地候选卡；不能为去重而跨未知账号边界拼接。

有可信 scope 与已验证局部成员证据时，正式归属按原证据归约逐条生效，不等待所有项目证明齐备。当前生产正式账号、原生成员认证与正向 NONE 仍未获得新的实机通过证据；其实际状态须如实单列。

## 6. 升级与不变量

数据库名、version=1、12 个 store、已导入记录、网站、墓碑及历史 checkpoint 保留；可选字段是兼容扩展，不清库、不重导入、不改变账号分区。未知老记录缺少可选字段可直接按时间投影。页面只改必要的分组和能力说明，沿用首页设计、搜索、5/+12 展开和滚动锚稳定策略。

Free 无 AI/API/云服务；不采集正文、草稿、附件或完整会话 JSON，不修改原 VAIWL 仓库。唯一分支与 Draft PR #1 继续使用，main 不合并、商店不发布。
